001: Discarding the Batch Paradigm

2024-09-10
perf , c , workflow

Introduction ¬

Build times should be fast. Live in C++land for long enough and you might forget this, but just look at languages that have prioritized compiler performance, and its clearly viable. Go, Jai and Nim are a couple examples that come to mind. Nim is particularly interesting here because its literally generating C code, giving it to a C compiler and letting it generate the binary. This illustrates that C can be very fast to compile, if configured well.

I work across a few operating systems, so I use CMake, Ninja and Clang. If you are primarily using Windows and Visual Studio, I highly recommend checking out Sebastian Shöner’s excellent blog post on this.

I took to speeding up build times in my personal engine I use for making games, I’ll use this as an example throughout.

Measurement ¬

Just like any performance problem, our intuition can quickly lead us in the wrong direction, so it’s important we measure things. There are two broad steps I use to measure build times.

Global Compilation Stats

On a clean build directory, I run the build as usual:

cd build
cmake -GNinja -DCMAKE_BUILD_TYPE=RelWithDbgInfo ..
ninja

Once the build has completed we can use a handy tool called ninjatracing which consumes the generated .ninja_log file and generates JSON consumable by Chrome’s built in tracing (chrome://tracing) or perfetto.

At a quick glance in the first column (we focus our efforts here first, as the latter columns are doing final global steps like linking, more on that later), we can notice one particularly long compilation unit (in the thread 1 row), in sprintf.c. This is pulling in STB’s sprintf implementation. Moving to the next type of profiling, we can examine why this particular file is taking a long time.

Local Compilation Stats

Once we have a problem unit to hone in on, we can use Aras’ wonderful contribution to clang, -ftime-trace. To enable this in cmake we simply need to add the following to our CMakeLists.txt.

add_compile_options(-ftime-trace)

From this we will get a json file output for each .o file generated in the build process. Once we run the build, we can examine our known problem file.

Linking

For linking I have one recommendation for *nix users, use Mold. If possible, please throw some financial support the developers way. It is a massive leap over Gold, Ld, and Lld in terms of performance. How Epic or any of the other money printers with tools full of a butt ton of DLLs hasn’t paid Rui to integrate Windows support is beyond me.

Closing

With some careful planning and consideration, build times can be very fast.

  1. Measure it, automate that measurement example gh action
  2. Keep your headers free of superfluous and heavy includes.
  3. Bake build items that are rarely changing.
