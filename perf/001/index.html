001: Contiguous Memory

Motivation

Default behaviors, both in systems as well as in people, are incredibly important. The data structures we use day in and day out have a huge impact on performance. While things like asymptotic complexity do have value, I believe the current calculus employed by the average programmer is a bit skewed in the wrong direction. Particularly, I think they are considering things like asymptotic complexity before considering the memory layout of a particular data structure. For the vast majority of situations, this is the wrong approach.

The rate of increasing speed for processors has dwarfed that of their memory counterparts. When Big-O notation(the common way of discussing asymptotic complexity) was forumlated, the cost of a memory access was within the same magnitude as the cost of computation. These days, that isn’t remotely true. We must consider the memory subsystem first if we care about performance, and next consider the efficiency properties of our approach. In short, we need a better default way of thinking.

The first data structure you should be reaching for, should almost always be an array. A contiguous layout is the most amenable thing we could give to a modern CPU. Contrast this with other data structures, such as a map, or a list, which have heaps of indirection, causing countless stalls when we need to iterate through that data.

CPUs don’t grab data one byte at a time, data is fetched in cacheline sizes, typically 64 bytes, but can differ (32 bytes on a Pi, 128 bytes on the new apple silicon). Because of this when you fetch something from a non-contiguous data structure, like a linked list, you are essentially wasting the remainder of that cacheline being pulled along for the ride. With an array, its all able to be immediately utilized by the CPU.

Initial numbers

To demonstrate this, lets whip up a quick benchmark, simply iterating through a set of data, stored in a vector, and a linked list. We’ll use google’s excellent benchmark library to get some reasonably statistical results. (While I’m not a fan of the STL, we use it for readers' familiarity & comfort below).

#include "benchmark/benchmark.h"

#include <forward_list>
#include <vector>
#include <cstdint>

#define BENCH_SIZE 1'000'000

static void BM_Iterate_Array(benchmark::State& state) {
  // set up code, not benchmarked
  std::vector<int32_t> v;
  v.reserve(BENCH_SIZE);
  for (int i = 0; i < BENCH_SIZE; i++) {
    v.push_back(i % 13);
  }
 
  // the actual portion being benchmarked
  for (auto _ : state) {
    int32_t sum = 0;
    for (const auto& item : v) {
      sum += item;
    }

    // preventing the optimizer from just deleting our code
    // since it doesnt get used anywhere else.
    benchmark::DoNotOptimize(v);
    benchmark::DoNotOptimize(sum);
  }
}
BENCHMARK(BM_Iterate_Array);

static void BM_Iterate_List(benchmark::State& state) {
  std::forward_list<int32_t> l;
  for (int i = 0; i < BENCH_SIZE; i++) {
    l.push_front(i % 13);
  }

  for (auto _ : state) {
    int32_t sum = 0;
    for (const auto& item : l) {
      sum += item;
    }

    benchmark::DoNotOptimize(l);
    benchmark::DoNotOptimize(sum);
  }
}
BENCHMARK(BM_Iterate_List);

BENCHMARK_MAIN();

Running on my macbook (M1, 2020), we get the following result (note, I ran this on a modern ryzen threadripper and intel chip recently as well with similar results):

BM_Iterate_Array      47584 ns        47584 ns        14893
BM_Iterate_List     1077503 ns      1043300 ns          669

Iterating the data is takes 22x as long through a linked list in this result. Not great.

Other considerations

These discontiguous structures often have other useful algorithmic properties, such as quick removals and insertions when compared to the default array implementation. While this is true for the default implementation on something like std::vector, we can actually recover this O(1) removal behavior and insertion, with better overall performance.

For example, if retaining order isn’t important to us, we can simply do a ‘swap-remove’, in which we swap the to-be-removed element with the last element, and just decrement the size of the buffer. (Note, there are other tricks, such as tombstone’ing if order is important, an exercise for the reader).

This shows us that considering the specifics of our problem, often opens up our ability to shed assumptions forced on by a particular implementation. In doing so, we retain our paramount property of cacheline density, whilst recovering algorithmic efficiency approaches of other data structures, nice!

Keeping things open

Another key aspect of utilizing cache friendly data structures like an array is that it opens up the possibility for further optimization. Particularly, shrinking our data types being stored in the array has a direct impact on cacheline density.

Going back to our array iteration benchmark, we can look what happens if we try compacting our data. The results are mostly in line with intution: cache is a finite resources, smaller data = more per line = faster processing. The one caveat here is a slight slowdown of u8 vs u16 (0.006ms), likely due to some unfortunate conversions happening in the generated assembly. Beyond that, we get a 2x speedup from u64 to u32, and from u32 to u16.
